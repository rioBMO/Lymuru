# 2026-11-18 — Per-user data directory + NSIS installer

## Problem

The app stores its database, logs, and Telegram session in `data/`, resolved
relative to the **current working directory**:

- `main.go` → `storage.Open("data/lymuru.db")`, `backend.InitLogger("data")`
- `app.go` → `NewDeezerSidecar("data", …)` (twice), `OpenConfigFolder()` uses `cwd/data`

The NSIS installer (`wails build -nsis`, install scope `machine`) puts the app in
`C:\Program Files\Lymuru`, and its shortcuts start the app with that folder as
the working directory. Normal users cannot write there, so `storage.Open` fails
and `log.Fatalf` kills the process. Because the binary is a GUI-subsystem
executable, the user sees nothing: the app just doesn't open.

## Changes

1. **`backend/datadir.go` (new)**
   - `ResolveDataDir()` → `$LYMURU_DATA_DIR` if set, otherwise
     `os.UserConfigDir()/Lymuru` (`%APPDATA%\Lymuru` on Windows).
   - `LegacyDataDirCandidates()` → `<exe dir>/data`, `<cwd>/data`.
   - `MigrateLegacyDataDir(dst, candidates)` → if `dst/lymuru.db` does not exist,
     copy the top-level files (db, `-wal`, `-shm`, `*.session`) from the first
     candidate that has a `lymuru.db`. The DB file is copied last via
     temp file + rename, so a failed copy never leaves a half-written DB that
     would block a retry. Originals are left untouched.
2. **`main.go`**: resolve the data dir → init the logger → migrate → open the DB
   with absolute paths. Startup failures are written to the log and shown in a
   native message box instead of exiting silently.
3. **`app.go`**: `App` stores `dataDir`. The sidecar and `OpenConfigFolder` use it.
4. **Settings UI**: the Deezer "Session File" hint stops saying `data/…`.
5. **Docs**: update the data path in `README-dev.md` and `AGENTS.md`.
6. **Installer**: install NSIS locally (`winget install NSIS.NSIS`) and build
   with `build.ps1` (`wails build -nsis`).

Out of scope: the Deezer sidecar script (`sidecar/deezload.py`) is not shipped
in the installer (same as today's portable EXE). The FFmpeg directory
(`~/.lymuru`) is unchanged.

## Testing strategy

- **Unit tests** (`backend/datadir_test.go`):
  - `LYMURU_DATA_DIR` override is respected and made absolute.
  - Migration copies db, wal, and session files; skips subdirectories.
  - Migration is a no-op when the target already has `lymuru.db`.
  - Migration is a no-op when the source and target are the same directory.
  - Migration with no candidate DB returns an empty source.
- `go vet ./...` and `go build ./...`.
- `wails build -nsis` must produce `Lymuru.exe` and `Lymuru-amd64-installer.exe`.
- Manual: install → launch from the Start Menu → confirm that
  `%APPDATA%\Lymuru\lymuru.db` and `logs\lymuru.log` are created.
  Note: on this dev machine, Smart App Control blocks unsigned binaries,
  including `go test` executables, so tests run under WSL/CI or on a machine
  without SAC enforcement.

# Follow-up — remaining open issues

## 1. Deezer sidecar missing from installed/portable builds

`resolveSidecarScriptPath()` only finds `sidecar/deezload.py` next to the EXE,
two levels up (dev `build/bin`), or in the cwd. The installer and the portable
EXE ship neither, so Deezer never starts outside the repo.

- Embed `sidecar/deezload.py` + `sidecar/requirements.txt` into the binary
  (`//go:embed` in `main.go`, handed to `backend.SetEmbeddedSidecar`).
- Keep the on-disk candidates first (so `wails dev` uses the live repo copy);
  fall back to extracting the embedded files to `<dataDir>/sidecar/`, rewriting
  only when the content changed.
- When the process dies with `ModuleNotFoundError`, report the exact
  `python -m pip install -r <requirements.txt>` command instead of a raw traceback line.

## 2. Wails version drift

`go.mod` pins `wailsapp/wails/v2 v2.12.0`, while the CLI (local and CI, installed
`@latest`) is v2.17.0, which triggers a warning on every build.

- Bump the module to v2.17.0 (`go get` + `go mod tidy`).
- CI workflows and `build.ps1` install the CLI at the version read from `go.mod`
  (`go list -m`), so they can't drift again.
- Workflows use `go-version-file: go.mod`. `build.yml` pinned Go 1.21 while
  `go.mod` requires 1.25.

## Not fixable in code

Smart App Control blocks unsigned binaries. That needs a code-signing
certificate (e.g. Azure Trusted Signing) or SAC turned off; it is documented, not changed.

## Testing strategy

- Unit tests: embedded sidecar extraction (writes both files, skips an unchanged
  rewrite, errors when nothing is embedded).
- `go vet` (windows + linux), Linux test binary run under WSL (SAC blocks local tests).
- `.\build.ps1 -SkipBindings` must build cleanly with no Wails version warning.
- Inspect the built EXE for the embedded script (string search) since it can't be launched here.

## Workflow consolidation

`build.yml` and `release.yml` both published a GitHub Release on `v*` tags.
They are merged into one `release.yml` (tag push → test, build via `build.ps1`,
publish; manual run → artifacts only). `ci.yml` keeps the push/PR checks.

# Follow-up — Deezer settings UX trap

Found while testing the installed build: credentials were saved but
`sidecar_enabled` stayed `0`, so Deezer never started.

## Problems

1. "Save Credentials" is enabled by the *unsaved* toggle, but only the page's
   main Save persists the toggle, so it's easy to leave without enabling Deezer.
2. Saving the toggle doesn't start/stop the sidecar; that only happens at app
   launch (or via "Restart Sidecar").
3. Python installed while the app runs isn't found (PATH is read at launch), and
   a Python install without "Add to PATH" is never found.
4. `DeezerSidecar.Stop()` closes the events channel while the stderr reader may
   still send on it → possible `send on closed channel` panic. Runtime
   start/stop makes this more likely.

## Changes

- Settings UI: after saving credentials, persist `sidecarEnabled = true` (and the
  Python path field) if it wasn't saved yet.
- Backend `SaveSettings`: when Deezer is enabled and the sidecar isn't running,
  or the Python path changed, start it; when disabled, stop it.
  `SetSidecarCredentials` restarts a running/enabled sidecar so new credentials apply.
- One `startSidecar`/`stopSidecar` path (startup, restart, settings) with a
  mutex around `a.sidecar`; goroutines use the local instance, not the field.
- `resolvePython` falls back to standard Windows install dirs, newest version first.
- The events channel is closed by its only sender (the stderr reader) when the
  process's stderr ends; `Stop()` no longer closes it.

## Testing strategy

- Unit tests: newest-Python selection (numeric, so 3.10 > 3.9).
- `go vet`, `go test ./backend/...`, full `build.ps1`.
- Manual on the installed app: disable Deezer and Save (sidecar process exits),
  enable and Save (it starts and reconnects from the saved session without a new code).

# Follow-up — version metadata after the v1.1.0 release

## Findings

- The UI version (`__APP_VERSION__`) comes from `frontend/package.json` via
  `npm_package_version` (still `1.0.0`). The release workflow only rewrites
  `wails.json`, so even the v1.1.0 release shows "v1.0.0" in the header and the
  update dialog. Go's `GetVersion` (embedded `wails.json`) was already correct.
- The update check compares versions as strings (`"1.10.0" > "1.9.0"` is false).
- `wails.json` in the repo still says `1.0.0`; `CHANGELOG.md` has no 1.1.0 entry.
- Windows file properties are **fine**: Explorer shows 1.1.0 for the release EXE.
  The empty values came from Windows PowerShell's .NET `FileVersionInfo`, which
  doesn't read Wails' language-neutral (`0000`) block. No change needed.

## Changes

- `wails.json` is the single version source: `vite.config.ts` imports
  `../wails.json` (`resolveJsonModule` in `tsconfig.node.json`), and the unused
  `version` field is removed from `frontend/package.json` (private package).
- `frontend/src/lib/version.ts`: numeric `compareVersions` / `isNewerVersion`,
  used by the update check.
- Bump `wails.json` to 1.1.0; add a 1.1.0 (and dated 1.0.0) entry to `CHANGELOG.md`.

## Testing strategy

- `bun test` for `version.ts` (numeric ordering, `v` prefix, suffixes, unequal lengths).
- `bun run build` and grep the bundle for the injected version.
- Full `build.ps1`: the EXE's embedded `wails.json` and the frontend bundle both say 1.1.0.
